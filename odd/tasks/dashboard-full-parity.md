# Full React Dashboard Parity

## Objective
Migrate the complete visible legacy dashboard experience to React with equivalent layout, information architecture, controls, and interactions, while retaining the already-decided truthfulness corrections for unknown amounts, dates, percentages, and income claims.

## Target
Port every capability that actually rendered in the legacy runtime:
- app chrome, period heading/actions, account/Gmail/settings surfaces;
- hero spending and balance cards;
- category distribution visualization and detail;
- daily/weekly spending chart, totals, and selected-day detail;
- period story, metrics, insights, and kind breakdown;
- movements filters, sorting, row detail/edit/remove, selection and bulk category actions;
- financial-period setup/edit visual flow and its calendar-oriented interaction where it carried visible behavior.

Dead/unreachable legacy code remains excluded. No new server contract is required unless a visible legacy interaction has no existing endpoint; such a gap must be reported before implementation.

## User decision
Use parity with veracity: match visible layout, copy intent, information, and interactions, but do not reproduce misleading legacy calculations or claims. Unknown amounts/dates remain explicit; date handling remains timezone-safe; no fabricated budget/income/progress values.

## FP-11 delivery record — tab-scoped financial dashboard cache (no request on F5)
- **User decision.** A browser reload (F5) of the authenticated dashboard must not request the financial cycle or the period movements again; the already-loaded period and its movements must stay exactly as the tab last saw them.
- **Cache.** `src/client/api/client.ts` gains a `sessionStorage`-backed cache under the versioned key `gastos-controlados:financial-dashboard:v1`. `readFinancialDashboardCache` returns the stored response only after a shape check (`cycle` with null-or-valid `selectedPeriod`/`incomeAmount`/`completedAt`, array `transactions`, null-or-string `warning`), so absent, denied, unparsable, truncated or older-shaped entries are all treated as a miss. `writeFinancialDashboardCache` swallows denied/quota writes. New loaders: `loadFinancialDashboardWithCache` (cache-first; on a miss runs the unchanged `loadFinancialDashboardData` and stores the result) and `refreshFinancialDashboardData` (always fetches and replaces the stored response). The existing `loadFinancialDashboardData(signal?)` contract is unchanged, so its direct callers and tests are untouched.
- **Wiring.** `FinancialSummary`'s mount effect uses `loadFinancialDashboardWithCache`, so the first load fetches and caches and an F5 returns the cache with zero requests; `retryToken > 0` (the `Reintentar resumen financiero` button and the cycle-setup save) uses `refreshFinancialDashboardData`. `reloadFinancialDashboard`, shared by create/edit/remove/bulk/Gmail sync/period change, also uses `refreshFinancialDashboardData`, so every explicit mutation or sync bypasses the cache and refreshes/stores current data. `StrictMode` is safe because the cache-first branch is keyed on `retryToken === 0`, not on effect run count. Demo data (`DemoDashboardPage`) and the session/auth check (`getSessionProfile`) never touch this cache.
- **Tests.** Added one focused test to `test/react-vite-foundation.test.js` covering cache hit (zero requests, exact period/movements), corrupt JSON fallback, valid-JSON-but-wrong-shape fallback, force refresh (fetch + cache replacement) and denied storage (read miss, silent write, normal load). It stubs `sessionStorage` because Node 24 has none and discovers the key through the client writer instead of hard-coding it.
- **Evidence.** Focused cache test passes 1/1. Full `test/react-vite-foundation.test.js`: 85 tests, 81 pass, the same 4 pre-existing stale English/legacy source assertions (`Unable to load the account`, `react-spending-breakdown`, `Unidentified expense`, `Pending amounts`) unchanged. `npm run build` passes (main 392.81 kB / 114.61 kB gzip; ECharts lazy 1,135.02 kB / 381.54 kB gzip; CSS 61.34 kB / 9.17 kB gzip). No server/API change, no new dependency, no localStorage.
- **Stale-cache tradeoff.** A data change that happens outside this tab (another tab, direct API use, background Gmail import) is not seen on F5 until the user performs an explicit action (retry, period change, create/edit/delete/bulk, Gmail sync), which forces a fresh request. This is the accepted cost of serving the tab cache; a new tab, a closed tab, or an explicit mutation starts from current server data.
